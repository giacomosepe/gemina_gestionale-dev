## Words
- **staff** = Gemina's team, mirrors the Zite table Ruoli (Amministratore → `admin`, Manager → `manager`). `former_staff` = left the team: no access, profile kept for history.
- **partner** = a segnalatore (referrer). In the Gestionale's screens Gemina's own people are called *Manager*.

## Rules
1. Every change is a file in `migrations/`, applied to dev first, tested, then to production. Never edit production by hand.
2. Only the publishable key may appear in a browser or a Zite page. Secret keys and bridge secrets live only in Supabase / Zite secret stores.
3. After every change: run the tests in `tests/` and the security advisor.

## Settings that are not SQL (set once per project)
- Auth: sign-ups disabled; site URL and redirect URLs; leaked-password protection or password sign-in off.
- Edge Function `portal-bridge` deployed (verify_jwt off: it checks its own secrets), with secrets `BRIDGE_SECRET_STAFF` and `BRIDGE_SECRET_PORTAL` (different values).
- Staff accounts are not created by hand: the bridge makes them from the Gestionale's Ruoli (see migration 20261020183659).
- Bridge action `notify` (both secrets): Zite's bell events for one current staff member. With the portal secret only the
  Portal's own events (messaggio-segnalatore, nuova-segnalazione, primo-accesso) and segnalatore links, and no actor.
  Kind `event` labels are Zite's bell text: a future unread-email job must skip them (Zite emails those itself).
- Bridge action `sync_partner` (staff secret): segnalatori created, edited, archived or deleted in the Gestionale update
  `public.partners` (deleted = archived). Edge Function settings: **production** `PARTNER_EMAILS_REAL=true`; **dev**
  `DEV_TEST_PARTNER_EMAILS` = Giacomo's test addresses (comma separated). Without them real referrer emails are replaced
  by placeholders (dev keeps no real referrer data). Archiving or an email change drops portal memberships at once;
  a deleted segnalatore is archived with its email released. Action `archive_missing_partners` (repair, run by the
  Gestionale's admin endpoint `sincronizzaSegnalatoriSupabase`) archives referrers that no longer exist in Zite.
- Referrer messages (step 6, migration 20261021133651): one conversation per referrer and subject; recipients = staff taking
  part (the colleague the referrer chose is added by bridge v6 `start_partner_conversation`); read by anyone at Gemina =
  read for the team (`staff_read_at`), referrer side `partner_read_at`; `public.partner_threads()`,
  `public.staff_colleagues()`, `public.mark_conversation_read()`. Referrers cannot create conversations from a browser.
- Message emails (Edge Function `message-emails`, verify_jwt off: it checks the internal secret): extensions `pg_net` and
  `pg_cron` (in the migration), cron job `message-emails-sweep` every 5 minutes, Vault secret `message_emails_secret`
  (generated by the migration). **Per project, once:** Vault secret `functions_url` =
  `https://<ref>.supabase.co/functions/v1` (`select vault.create_secret('<url>', 'functions_url');`); until it exists no
  email is requested. Edge Function secret `RESEND_API_KEY` (Giacomo, dashboard).
- History import of Zite messages: in one transaction with `select set_config('gemina.import', 'on', true)` and no user;
  never set it session-wide.
- Referrer documents (step 7, migration 20261021145534): files and links between Gemina and the segnalatori in
  `public.documents` and the private bucket `documents`. The browser creates the row (the server makes the path
  `partner/<partner>/<document>/<name>` and checks the scope), uploads with its own login, then calls
  `public.confirm_document_upload()`. Also `public.partner_documents()`, `public.remove_document()` (hides, the file stays),
  `public.notify_document()` ("Notifica segnalatore": bell + email, message-emails mode `document`),
  `public.mark_documents_read()`. A segnalatore's file outside a message → team bell (kind `document`) and the team email
  after 15 minutes, like messages.
- Automatic messages (migration 20261021155543): `messages.automatic` = a message signed Gemina Advisory with no sender, written
  only by the bridge (v7 action `post_automatic_message`, staff secret) for the Gestionale's own notices; only the segnalatore
  gets a bell, no Supabase email (Zite sends its own). "Notifica segnalatore" ignores a second press within a minute.
- Team documents and reminders (migrations 20261021221703 + 20261021221829): `documents.kind = 'team'` = Gemina's own files on a
  pratica (azione attachments; path `team/<pratica>/<doc>/<name>`, staff only, never shared, `zite_attivita_id` optional), listed in
  the pratica's «Documenti dal server». `public.reminders` (one per pratica and date key; staff write from the browser; recipients =
  Zite user ids) + `public.reminder_sends`; pg_cron job `pratica-reminders` every hour at :05 runs `private.send_due_reminders()`,
  which acts at 8 in Rome: bell (kind `event`, event `promemoria`, link `pratica:<id>`) and message-emails mode `reminders`.
- Azienda as home of team documents (migration 20261022145359, test 009): a `team` document always has `zite_azienda_id`
  (path `team/<azienda>/<doc>/<name>`), may be about a trattativa and/or a pratica, and has `lifespan` `company` (default:
  serves every project of the azienda, e.g. bilanci with `category = 'Bilancio <anno>'`) or `project` (needs a trattativa or
  pratica). Views read across (a pratica shows the azienda's documents and its own); nothing is copied. Bucket limit 50 MB.
  A reminder is about exactly one pratica or trattativa (`zite_trattativa_id`); the bell links `trattativa:<id>` for the latter.
- Qonto documents (migration 20261023124424, test 010): `public.qonto_documents` = one row per Qonto invoice or credit note (drafts not
  imported; `qonto_id` unique; integer cents `total_cents`, `vat_cents`, `net_cents` = total - VAT; `status_qonto` raw, `status`
  Emessa / Incassata / Annullata as Zite `statoDaQonto`; `paid_at` null when Qonto has none; `company_id` nullable, `zite_pratica_id`
  filled in M2; "Scaduta" is never stored, views derive it) and `public.qonto_sync_runs` (counts and error per run). Staff read only;
  partners and clients nothing; writes only by the service role (the qonto-sync function).
- Companies and Qonto (migration 20261023125510): `companies.vat_number` (partita IVA, text) and `companies.qonto_client_id` (unique where set), filled from
  Zite Aziende ("P.IVA", "Qonto ID") by the idempotent script `scripts/backfill_companies_qonto.sql` (run 2026-10-23: 4 Qonto ids, 21 VAT numbers;
  3 Zite aziende with a P.IVA have no Supabase company: Appennino Food Group, Podartis, Technowrapp). Re-run the script after new aziende get a Qonto ID in Zite.
- Qonto sync (Edge Function `qonto-sync`, verify_jwt off: it checks its own secret; migration 20261023125951): GET-only fetch of Qonto `/client_invoices`
  and `/credit_notes` (paginated) into `qonto_documents`, one row in `qonto_sync_runs` per run (counts, unmatched companies, skipped drafts, newly
  removed, error). Credit notes are stored negative; a document Qonto stops returning gets `removed_at` (never deleted). Call: `POST` with header
  `x-sync-secret` = Vault secret `qonto_sync_secret` (generated by the migration; the schedule of PRDDISC-5 reads it from Vault). Edge Function secret:
  `QONTO_LOGIN` (Qonto API credential, set in the dashboard by Giacomo; never in the repo). Answer 200 `{ok, fetched, inserted, updated, unmatched,
  skipped, removed}`, or 502 with the error (also saved in the run row). A second run with no change in Qonto reports 0 inserted and 0 updated.
- Qonto schedule (migration 20261023130928, test 011): pg_cron job `qonto-sync-nightly` (every hour at :00; `private.qonto_sync_nightly()` waits for 02:00
  Rome, summer and winter time alike, starts one sync a day and retries a failed one up to 3 runs a day) calls `qonto-sync` through pg_net with the Vault
  secrets `functions_url` and `qonto_sync_secret`. Job `qonto-sync-check` (every hour at :20, `private.check_qonto_sync()`): if the latest `qonto_sync_runs`
  row failed, or started more than 26 hours ago, every admin (`staff_role = 'admin'`) gets one bell notification (kind `event`, event `qonto-sync`, no link,
  no email); `event_key` makes each problem arrive once. With no run at all the check is quiet.
- Invoice views (migration 20261023131450, test 012), all `security_invoker` so the RLS of `qonto_documents` applies (staff read; partners nothing):
  `invoice_status_v` (every document, `status_visible` = Scaduta when Emessa and due before today in Rome, `days_overdue`, `removed` flag),
  `invoice_payments_v` (paid invoices with `issue_date` and `paid_at`; `needs_review` when paid but no date), `invoice_vat_v` (net, VAT, total per
  document by issue date, Annullata and removed left out), `invoice_vat_month_v` and `invoice_vat_quarter_v` (the same summed; credit notes are already
  negative). No DSO in the database (the app computes it from `issue_date` and `paid_at`).
- Review list (migration 20261023133334, test 013): `invoice_review_v` lists invoices Qonto left incomplete: Emessa without a due date (never Scaduta; `due_date_missing`)
  and Incassata without a payment date (`paid_at_missing`; `paid_at` stays null, never the issue date, so DSO is not distorted). Credit notes are not review cases.
  Until a credit note and an overdue invoice exist and `scripts/reconcile_qonto.sql` has been re-run, Zite stays the source for screens the team relies on.
- Pratiche mirror (migration 20261023143448, test 014): `public.pratiche` is a read-only copy of the Zite pratiche, keyed by the Zite UUID (the later full migration only adds
  columns): `code`, `company_id` (resolved from `zite_azienda_id` through `companies`), `status` (Zite label as is), `is_open` (Zite: not Fatturazione completata, not Interrotta),
  `total_fee_cents` (= Zite "Commissioni totali", `valorePratica`, net of VAT: Zite computes it, Supabase never does), `removed_at`, `synced_at`. Staff read only. Bridge actions
  (staff secret, bridge v9): `sync_pratica` (one pratica, called by the Gestionale after a pratica is created or its Stato, Azienda or fees change; a failed push never blocks the
  save) and `resync_pratiche` (repair: all pratiche in one call, 150 at most; the ones Zite no longer has are marked removed, never deleted). Both end in `private.sync_pratiche`. Zite side (commit 9e988bc in the Zite workspace, 2026-10-23): `lib/supabase/sincronizzaPratica.ts` (4 s timeout, never throws), called only from the pratica writers
  (`nuovaPratica`, `salvaPratica`, `valoriInfoProgetto`, `scriviColonna` for the pratica) and the admin endpoint `sincronizzaPraticheSupabase` (repair). Staff secret and bridge URL are the ones `sincronizzaSegnalatore` uses.
- Invoice to pratica link and payment status (migrations 20261023145446 + 20261023145553 (fix), test 015): `qonto_documents.pratica_id` (FK to the mirror) + `pratica_link_source` (auto / manual / zite); `zite_pratica_id` is kept and filled. Rule as in
  Zite: the company's one open pratica, else its one pratica in total, else unlinked and listed in `review_invoices_v` (also: company differs from the pratica's). The rule only fills documents with no link, on insert/update of
  the document and whenever a pratica is synced; manual links (`private.set_invoice_pratica`, service role only) and links copied from Zite (`scripts/backfill_invoice_pratica.sql`) are never overwritten. `pratica_payment_status_v`:
  `total_fee_cents`, invoiced and paid net (Incassata, credit notes subtracted, cancelled left out), outstanding, `payment_state` partial / fully_paid / overpaid (tolerance 1,000 cents from `private.fully_paid_tolerance_cents()`),
  `needs_review` (overpaid or no total), `archivable` (= fully_paid; whether the pratica is also closed is not decided, `is_open` is in the view).
- Referrals mirror (migration 20261023154802, test 016): `public.referrals` is a read-only copy of the Zite Segnalazioni (segnalatore x azienda), keyed by the Zite UUID: `partner_id` / `company_id` (resolved from the Zite ids through
  `partners` / `companies`), `commission_pct`, `starts_on` (Dal), `duration_years`, `ends_on` (Scadenza, as Zite stores it), `removed_at`, `synced_at`; the free-text note is not mirrored. Staff read only (the segnalatore's own view comes
  with PRDDISC-14). Bridge v10 actions (staff secret): `sync_referral` (one, after a segnalazione is created, edited or deleted in Zite) and `resync_referrals` (repair: all, 150 at most; the missing ones are marked removed, never
  deleted). `private.referral_active_on(referral, date)` = Zite's `attiva()`: Dal <= date <= Scadenza, an empty side is open, removed or unknown = false.
- What a segnalatore sees of the payments (migration 20261023155528, test 017): `public.partner_payments()` is the only window and the only segnalatore path to the invoices. It returns one row per paid invoice (status Incassata, with a
  payment date, not a credit note, not cancelled, not removed in Qonto) of a client the calling segnalatore referred, where the referral was active on the invoice's issue date (`private.referral_active_on`; a referral removed in Zite never counts):
  invoice number and id, company name, pratica code (null if unlinked) and `paid_at`. No amounts, no unpaid or overdue invoices. The caller is checked inside (a current member of a non-archived segnalatore; staff, clients and anyone else get
  zero rows; anonymous cannot call it); archiving the segnalatore or removing the membership ends it at once. The policies and grants of `qonto_documents`, `referrals` and the views are unchanged (staff only). No bridge action or screen yet.
- Commissions (migrations 20261023162254 and 20261023163202, test 018): `public.commissions` holds one line per invoice and referral (unique on both): `pct` and `base_cents` frozen at creation (the base and amount may follow a corrected
  invoice until the line is received; pct, invoice, referral and partner never change), `amount_cents` = base x pct / 100 rounded half up (a table check; equals Zite's `round2` on euros), `partner_invoice_number` /
  `partner_invoiced_on`, `paid_on`. The table refuses a line for a credit note, a cancelled or removed invoice, a negative base, or a partner that is not the referral's. `public.commission_stages_v` (security_invoker)
  gives the stage with Zite's names and order: Provvigioni teoriche (invoice not paid), maturate (invoice Incassata), fatturate (partner invoice number set), ricevute (`paid_on` set; wins over the rest).
  Staff read only, no partner policy; written only by the service role or the functions of the next issues (rebuild PRDDISC-20, marks PRDDISC-21). Backfill of Zite `Provvigioni`:
  `scripts/backfill_commissions.sql` (idempotent; Zite had 0 lines on 2026-10-23).
- Commission rebuild (migrations 20261023170220 and 20261023170331, test 019): `private.rebuild_commissions(invoice)` = Zite's `aggiornaProvvigioniFattura`. One line per invoice and referral active on the issue date
  (`referral_active_on`); the invoice must be a real invoice (not a credit note, not cancelled, not removed in Qonto) with an issue date, a net amount, a company AND a pratica (as in Zite, which finds the client through the pratica).
  Whole net amount, no exclusion. Percentage frozen at creation; the base follows a corrected invoice. **Lines with a partner invoice number or `paid_on` are never touched** (Zite protects only paid ones; the invoiced ones are protected here as the issue asks).
  `commissions.matured_at` is set the first time the invoice is paid (`clock_timestamp()`; a line born on an already paid invoice gets `matured_at = created_at`, so PRDDISC-22 fires only when `matured_at > created_at`).
  Triggers: `qonto_documents` (insert; update of kind, status, company, pratica, net amount, issue date, removed) and `referrals` (insert, update of company/partner/percentage/dates/removed, delete: rebuilds that company's invoices).
  A failing rebuild never breaks the save: it is written to `commission_rebuild_errors` (staff read; look at it after a sync). Repair: `public.rebuild_all_commissions()` (admins only; idempotent; returns the counts). First run at migration: 0 lines (no referral on the 4 real invoices' companies; Zite has 0 lines).
- Qonto sync button (portal-bridge v11, PRDDISC-18): action `run_qonto_sync` (staff secret; the caller must be an admin, else `admin_only`; refused with `sync_running` while a run started in the last 5 minutes has not finished).
  The bridge reads `qonto_sync_secret` from the Vault, calls the `qonto-sync` Edge Function and returns only the counts (`fetched`, `inserted`, `updated`, `unmatched`, `skipped`, `removed`, `run_id`, or `ok: false` with a short `error`).
  The run is logged in `qonto_sync_runs` by `qonto-sync` itself. Neither the Qonto key nor the function's secret ever reach Zite or a browser. Zite's endpoint is `sincronizzaQontoSupabase` (admin only).
- Marking commissions (migration 20261023223240, test 020): `public.mark_commissions_invoiced(ids, invoice_number, on_date)` (the segnalatore's invoice arrived: matured lines only; number required, date optional) and
  `public.mark_commissions_paid(ids, on_date)` (Gemina paid the segnalatore: invoiced lines only; date defaults to today in Rome). Staff only (checked inside), security definer, fixed search path, execute for signed-in users only.
  All the lines of a call succeed or none does (rows locked first); the answer is the lines as `commission_stages_v` shows them (the stage is read from that view). Messages are in Italian, as Zite's. Unlike Zite's endpoints, the stage is checked
  in the database (Zite checks nothing but the number; its screens only offer the right lines); un-marking a line paid (Zite `pagata: false`) is NOT available yet.
